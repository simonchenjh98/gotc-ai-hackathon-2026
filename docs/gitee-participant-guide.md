# GOTC 2026｜选手建仓与提交指南

从创建代码仓库，到保存正式提交回执。

**版本：2026-11-04 · 赛前教学版**

适用活动：2026 年 11 月 7-8 日，北京亦庄实验中学。

> 发布状态：Gitee 模板已创建，自助申请组织仓库与自动读取 SHA 的功能正在接入。2026-11-04 核对时，官网首页已可访问，但它链接的云端平台仍显示旧看板。本文是赛前教学版；新流程须经上线验收和主办方开放后使用。请从官网“提交作品”进入，不要自行猜测平台地址。

## 1. 先看懂：在哪里做什么

**官网申请仓库 → 主办方核对账号 → 接受本队仓库权限 → 上传代码 → 官网获取当前版本 → 预览并确认 → 保存回执。**

| 位置 | 你在这里完成什么 |
| --- | --- |
| Gitee 代码仓库 | 存放代码、README、运行说明与来源说明，和队友协作 |
| 官网作品提交页 | 使用本队提交码登录，登记正式版本与材料链接 |
| 正式提交回执 | 核对服务器收到的版本号、时间和完整 commit |

**Gitee 的 commit/push 不等于官网正式提交。保存草稿也不等于正式提交。**

常用入口：

- [Gitee 组织](https://e.gitee.com/gotc-ai-hackathon/projects)
- [GitHub 组织](https://github.com/GOTC-AI-HACKATHON)
- [参赛起步模板](https://gitee.com/gotc-ai-hackathon/gotc-2026-starter)
- [活动官网](https://etownyouthai.com/)
- [计划使用的作品提交页](https://8.141.114.201/gotc/platform.html#team)（待上线并由主办方开放）

## 2. 开始前准备好

1. 每位需要协作的队员准备自己的 Gitee 或 GitHub 账号，确认可以正常登录。
2. 向主办方确认本队的队伍编号、队名，以及哪位队员负责最终提交。
3. 准备需要写代码的队员的 **托管平台用户名或个人主页链接**。显示昵称可能重名，不要只报昵称。
4. 领取本队独立的官网提交码。提交码与 Gitee 密码是两回事，只在本队内保存。
5. 确认本队正式仓库和正式分支。同一作品只认定一个正式提交来源；其他镜像仓库用于备份。

当前组织有成员额度限制。**尚未获批加入组织时，不要反复建同名仓库，也不要向主办方发送密码、短信验证码或私人令牌。** 由主办方确认采用“组织分配仓库”还是“个人公开仓库”。

## 3. 在官网自助申请本队仓库（接入后）

1. 从 [正式官网](https://etownyouthai.com/) 点击“提交作品”，用本队独立提交码登录，核对队伍身份。
2. 在“本队代码仓库”区域选择主办方已启用的平台，填写本队 1-5 名开发者的平台用户名，点击“申请本队仓库”。此处填用户名，不填邮箱、昵称或主页链接；选手无需提供个人 Token。
3. 等待主办方核对用户名归属并处理申请。每个项目绑定一个正式仓库，主办方保留管理权，队员获得本队仓库的开发权限。
4. 按托管平台提示接受协作邀请（如有），通知主办方刷新邀请状态，再回到官网点击“刷新仓库状态”，查看仓库链接、正式分支和授权状态。显示“仓库已绑定”后再操作正式提交。
5. 点击已绑定的仓库，按第 4 节上传代码。已绑定后，正式提交的仓库地址和完整 commit 由系统取得，不再由选手手填。

平台未显示可用渠道或提示“尚未配置”时，联系主办方。组织容量、服务端授权和云端上线都需要主办方先准备好。

### 主办方手动分配或旧版备用流程

只有主办方明确启用备用流程时，才使用以下方式。不要同时申请多个正式仓库。

### 方式 A：主办方分配组织仓库

1. 把队伍编号、项目英文短名和 Gitee 用户名交给主办方。
2. 主办方在组织“代码 → 新建仓库”中选择“基于模板创建（仅代码）”，使用“GOTC 2026 参赛项目模板”。
3. 每队一个仓库，建议路径为 `team-001-campus-map`。这里的 `001` 和 `campus-map` 只是示例，要换成本队信息。
4. 主办方将对应队员加入本队仓库，并赋予所需的开发权限。选手不需要企业管理权，也不需要其他队伍的写权限。
5. 打开收到的仓库链接，检查“归属、路径、成员”是否属于本队。看不到仓库或不能编辑时，把页面提示交给主办方处理。

**不要直接把模板仓库当作本队作品提交，也不要在公共模板里写本队代码。** 模板当前默认分支是 `master`；如果本队仓库使用 `main`，后续命令必须相应替换。

### 方式 B：经主办方确认后，创建个人公开仓库

此方式可用于组织成员额度不足时。是否允许使用，以主办方通知为准。

1. 登录 Gitee，在工作台找到“新建仓库”。
2. 归属选择本队指定的个人账号，填写项目名称与英文路径，例如 `team-001-campus-map`。
3. 创建并初始化 README。需要对外提交前，按 Gitee 当前页面提示完成公开仓库所需的设置和检查。
4. 仓库内只上传允许公开的项目材料。通过“管理/成员”添加确认过的队友，由队长统一维护权限。
5. 把仓库主页链接交给主办方登记，并用未登录窗口检查能否访问。不能匿名访问时，不要把它当作已经准备好的公开提交仓库。

企业界面的“项目”是管理容器；真正承载代码的是“代码仓库”。官网需要填写后者的标准主页地址。

## 4. 上传代码：选择一种方式即可

### 浏览器操作，适合第一次使用 Git 的同学

1. 打开本队仓库，确认分支选择器指向约定的正式分支。
2. Gitee 使用“上传文件”入口上传源代码；改 README 时可打开文件，点击“编辑”，进入 Web IDE。GitHub 可使用“Add file → Upload files”上传，或打开文件后点击编辑图标。
3. Gitee Web IDE 修改后点击“创建提交”，在“更改”处暂存文件，填写提交说明再提交。GitHub 上传或编辑后点击“Commit changes”，按提示完成提交。两边都要确认目标分支正确。
4. 回到仓库刷新，确认新文件和最近提交已经出现。只在编辑器中改好、未完成提交，线上版本不会更新。
5. 如果使用功能分支，先按本队约定合并到正式分支，再选择最终版本。

上传前排除 `.env`、密钥、密码、聊天记录、个人信息、数据库、依赖缓存和无关的大文件。依赖使用清单文件说明；视频和大型模型文件使用可访问的链接，不要直接塞进 Git 仓库。

### 命令行操作，适合已有开发环境的同学

从本队已创建的仓库开始。把第一行的示例地址替换成本队“克隆/下载”（GitHub 为“Code”）中提供的 HTTPS 地址；后续把文件夹名、分支名替换为官网展示的实际值。下例使用 `main`；从 Gitee 模板手动建仓时也可能是 `master`。

```sh
git clone https://gitee.com/YOUR-OWNER/YOUR-REPO.git
cd YOUR-REPO
git switch main
git pull --ff-only
```

把项目源文件放入克隆得到的文件夹，保留 `.git`，先编辑 `.gitignore`，再检查将要提交的内容：

```sh
git status
git add .
git diff --cached --stat
git diff --cached
git commit -m "完成核心流程和运行说明"
git push origin main
```

提交前核对差异中没有敏感内容。Gitee 提示认证时，在自己的设备上按其官方提示配置；不要把密码、令牌或私钥写进命令、README、截图或作品表单。

如果代码已经在另一个 Git 仓库，先向队内熟悉 Git 的同学确认迁移方案。**不要为了推送成功使用强制推送，也不要删除 `.git` 后反复重建。** 遇到冲突先保存本地修改，再合并。

## 5. README 要让别人能运行

模板里带有以下栏目，请全部替换为本队真实内容；未完成的部分明确写“未完成”。

- **作品与问题：** 为谁解决什么具体问题，核心功能是什么。
- **运行方法：** 环境版本、安装依赖、启动命令和打开地址；涉及外部服务时说明如何自行配置。
- **AI 使用：** 使用哪些模型或工具、承担什么任务、如何人工核验。
- **测试与局限：** 实测过哪些流程，发现什么问题，还有什么没有实现。
- **团队分工：** 用角色或经本人同意的公开署名描述贡献，不必放私人联系方式。
- **来源与许可：** 第三方代码、模型、数据、图片、字体的来源与使用条件；写清本项目许可证。

“用了开源代码”不等于可以任意重新授权。只为你们有权授权的内容选择许可证，保留第三方署名和许可要求。不要把模板中的示例或“待填写”当作完成证明。

## 6. 找到最终 commit，复制完整值

一个 commit 是一次已经保存的 Git 提交。分支名会指向后续新版本，完整 commit 可以指明某次具体提交。

自助申请流程启用后，官网会读取已绑定分支的当前完整 SHA。你只需要核对预览中的版本；下面的复制方法用于自行核验或主办方启用的旧版备用流程。

### 在 Gitee 页面复制

1. 等待最终代码 push 成功，打开本队仓库主页。
2. 选择正式分支，点击提交次数或“提交历史 / Commits”。
3. 打开最终一次提交，核对修改内容与提交说明。
4. 复制完整提交页面链接，或复制完整 commit SHA。Gitee Git 仓库通常为 **40 位十六进制字符**；官网也兼容 64 位完整 SHA。

### 在命令行核对

```sh
git rev-parse HEAD
git ls-remote origin refs/heads/main
```

第一条显示本地当前 commit，第二条显示远端正式分支的 commit。把分支名换成实际值；若最终提交应是该分支最新版本，两者应一致。不同则先检查有没有未推送或未合并的改动。

| 官网字段 | 正确填写方式 |
| --- | --- |
| 代码仓库 | `https://gitee.com/本队归属/本队仓库`，使用仓库主页 |
| 最终代码版本 | 本队仓库的 `/commit/完整SHA` 链接，或直接填完整 SHA |

不要填写组织项目页、个人主页、文件页、本地路径、ZIP 下载地址、分支名、tag 或页面上缩短显示的前几位 SHA。企业界面链接以 `e.gitee.com` 开头时，仓库主页请从“克隆/下载”的标准 Gitee 地址取得，并去掉末尾 `.git`。

## 7. 官网正式提交（上线并开放后）

### 第一步：登录本队

打开主办方发布的作品提交页，用本队独立提交码登录，核对队伍编号和队名。若页面只显示看板、没有作品提交入口，说明当前入口或发布版本还未准备好，联系主办方；不要在评分或投票页面尝试提交代码。

查看页面的提交窗口和北京时间截止。正式成功以服务器回执为准，不以你点击按钮的时刻为准，尽量提前完成。

### 第二步：填写材料，先保存草稿

| 栏目 | 准备内容 |
| --- | --- |
| 作品名称、项目介绍 | 项目介绍建议简洁；当前表单上限 600 字符 |
| 代码仓库、最终代码版本 | 公开 HTTPS 仓库主页，以及完整 commit |
| README、许可证说明 | README 的 HTTPS 链接；许可证说明必填，许可证文件链接选填 |
| 原型演示 | 演示 HTTPS 链接或本地演示说明，至少一项 |
| 展示材料 | 5-7 页展示材料的可访问 HTTPS 链接 |
| 演示视频 | 约 2 分钟核心流程视频的可访问 HTTPS 链接 |
| 来源与局限 | 模型、数据、图片和第三方代码的来源，以及未完成部分 |

以上材料规格依据现有官网，最终以主办方通知为准。使用无需申请访问权限的材料链接，并用未登录窗口检查。平台登记链接，不接收本地文件上传。

使用已绑定的组织仓库时，代码仓库和最终代码版本由系统读取，你不用填写这两项。其他材料仍由本队准备；先检查官网展示的仓库和分支确实属于本队。只有旧版备用流程才手填代码字段。

点击“保存草稿”后，确认服务器显示已保存。草稿允许暂缺材料，正式提交需要补齐必填项。

### 第三步：检查、预览、确认

1. 完成材料自查，勾选自查声明。
2. 点击“检查并正式提交 ↗”，按错误列表补齐缺项。
3. 系统取得已绑定正式分支的当前完整 commit；在预览中逐项核对仓库、分支、完整 commit 和材料链接。这时仍未正式提交。
4. 点击“确认正式提交”。
5. 看到“正式版 v… 已收到”后，核对服务器保存时间和完整 commit，复制保存本次记录；如页面提供请求编号，也一并留存。

如果预览后队友又推进了正式分支，系统应要求重新获取版本并预览。与队友约定由一人操作最终提交，避免确认期间继续推送。

刷新后检查“最近正式材料”。若已部署版本提供“正式提交历史”，可以读取每次正式提交的材料记录。

### 第四步：修改后的处理

截止前允许修改时，重新 push 后再次让官网获取当前版本、预览并正式提交。**继续 push 不会自动更新已经登记的正式版本。** 保存新草稿也不会更新评委看到的正式材料。

展示或路演已经冻结本轮材料时，重新提交不会替换该轮快照；请查看“本轮评审采用的材料”并联系主办方。回执保存填写内容和链接，不等于代码、演示文件或视频已被备份。

## 8. 常见问题与最后自查

**版本保留规则：不要 force push，不要删除正式分支或改写已提交历史。** 违规导致已提交 commit 或材料无法取得，由本队承担相应后果，并及时告知主办方。只做后续普通提交，保留旧版本历史；主办方会另行核对归档情况，官网回执本身不等于源码备份。

| 遇到的问题 | 先这样处理 |
| --- | --- |
| 仓库 404 或不能推送 | 检查账号、归属、仓库路径和本队权限，联系主办方核对 |
| 无法加入组织 | 可能涉及成员额度、审批或邀请未接受，由主办方处理，不要更换账号反复申请 |
| 显示正式分支已变化 | 先完成最终推送，再重新获取当前版本并预览确认 |
| 提示 commit 格式错误 | 从同一仓库复制完整 commit 链接或完整 SHA，去掉查询参数和片段 |
| 提示材料版本冲突 | 先复制当前输入，读取服务器最新草稿，人工合并后再提交 |
| 网络中断或结果待确认 | 保存输入与请求编号；若有“查询这次请求结果”，先查询。没有查到不等于失败，勿连续重发 |
| 窗口关闭或已截止 | 联系主办方；改电脑时间、反复刷新不能延长服务器截止 |
| 不慎提交密钥 | 立即停止分享，联系主办方并到密钥所属平台撤销或更换；只删文件不能撤销泄露 |

提交前逐项确认：

- [ ] 仓库属于本队，正式分支和最终代码已核对。
- [ ] 最终代码已 push，官网预览中的完整 commit 正确。
- [ ] README 能带别人完成安装和运行。
- [ ] 来源、许可证、AI 使用和未完成部分写清楚。
- [ ] 仓库和材料链接在未登录窗口可访问。
- [ ] 原型、展示材料和视频都有本地备份。
- [ ] 仓库和材料中没有隐私、密码、提交码或 API 密钥。
- [ ] 官网显示正式版已收到，已保存回执。

最后记住：**Gitee 保存代码；官网确认提交；回执确认服务器收到了哪一版。**
