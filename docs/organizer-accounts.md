# Named organizer accounts

An organizer signs in with a case-insensitive ASCII username, a generated access code and a six-digit authenticator code. The platform stores the account, access-code hash, seed fingerprint, portal confirmation and last accepted time step in SQLite. It reads the Base32 seed from the operator's private `organizer-totp.json` credential. The gateway service does not need this credential.

## Enroll and activate an organizer

1. Use the installed service Python and a protected terminal. Run `python -m backend.gotc.admin_auth prepare --username organizer.example --name "Example Organizer" --out /private/staging/enrollment.json`. The command creates a new mode-0600 file. Use a mode-0700 staging directory on private encrypted storage, outside the event, release and backup directories. Deliver the access code to the organizer's password manager and the seed to their authenticator (SHA-1, six digits, 30 seconds).
2. In your private credential manager, add the lowercase username as a JSON object key and the corresponding 32-character Base32 seed as its string value. Preserve the other organizers' entries. Publish the complete mapping atomically, owned by root or the service user, mode 0400 or 0600. On systemd, provision `LoadCredential=organizer-totp.json:/etc/gotc/credentials/organizer-totp.json` on **gotc-platform.service**. Refresh the platform service's credential mount after changing the source file. When `CREDENTIALS_DIRECTORY` is set, this map is read exclusively from that directory. For an event running locally without systemd credentials, the loader reads the same filename under the private event data directory.
3. Run the activation command **as the service user, with the same mounted credential directory the platform is currently using**. On a systemd host this is normally `CREDENTIALS_DIRECTORY=/run/credentials/gotc-platform.service`. Use the actual runtime mount, since editing the root-owned source does not update an existing mount. Local development uses the same event directory and credential settings as the local server.

   ```sh
   python -m backend.gotc.admin_auth activate --data-dir /private/event --enrollment /private/staging/enrollment.json
   ```

   Enter the authenticator code at the hidden prompt. Activation requires the installed mapping to match the enrollment seed. Verification failure preserves the current accounts and sessions. Successful local enrollment consumes that time step and stages the account. Until the first named portal login succeeds, the existing legacy organizer credential and sessions remain available, including across a restart.
4. Wait for the next authenticator code and sign in to the organizer portal with the username and access code. The running platform must read the matching seed from its own credential source. On success, one transaction confirms the named organizer, consumes the code, issues the session and disables all legacy organizers and their sessions (including delegated team sessions). A missing or stale platform mount leaves the enrollment pending. Refresh the platform credential and retry with a current code. Remove the temporary enrollment file after delivering the access code and completing activation. Clear any temporary copies from the editor, transfer tool or clipboard. The prepare and activation commands also print a cleanup reminder. Retire obsolete shared organizer credentials while keeping any judge configuration still in use.

Repeat this procedure for additional organizers. Reserve a second enrolled account for recovery. A duplicate username is rejected. The platform accepts a one-step clock tolerance in either direction and consumes each time step once. [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)

## Revoke and recover

For a lost authenticator, enroll a new, distinct username locally. Run `python -m backend.gotc.admin_auth revoke --data-dir /private/event --username old.organizer` using the same credential view as the platform. Revocation disables the account and removes its sessions. At least one other active named organizer must have both a matching installed seed and a successful portal login. Then remove the revoked entry from the credential manager, refresh the delivered map and dispose of superseded credential material per the organization's retention policy.

Back up the organizer credential separately in the operator's encrypted credential store. The event database backup and installer backup omit the seed map. A full directory snapshot of a *local* event would include a map stored there, so exclude the map or protect and inventory that snapshot as a credential backup. Keep the other required event keys with their corresponding recovery sets.

After restoring a database, provision the matching map for all active, portal-confirmed organizers before starting the platform. A missing or mismatched confirmed entry stops platform startup. Restoring a stale database also restores its earlier account, session and replay state. Keep traffic closed, reconcile subsequent revocations, invalidate restored organizer sessions and wait until all previously accepted codes are outside the one-step tolerance before reopening. If all confirmed bindings are permanently lost, stop the services and keep traffic closed. Install a fresh map, stage a replacement with the local activation command, and run the local revoke command for each lost username with the explicit flag `--offline-recovery`. This permits a staged replacement when the target credential is unavailable. Restart with the replacement map, confirm its portal login privately, then reopen traffic. Previously retired legacy accounts stay disabled throughout recovery. A compatible gateway process can run independently during platform recovery.

## Earlier local development checkpoints

Unreleased development databases (schema version 2 or 3) can contain a plaintext `named_admins.totp_seed` column. Startup and event backup commands refuse these databases. Production databases predating named enrollment follow the ordinary schema upgrade.

1. Stop every process using the development database, including both services. Preserve the old development recovery set in encrypted storage under your existing secret-retention policy. Existing backups and snapshots of that schema still contain seeds. Allow temporary space for SQLite `VACUUM` (up to twice the database size in additional free space).
2. Provision the full username-to-seed mapping, including revoked entries, from your credential vault if available. To recover the mapping from the checkpoint, explicitly run `python -m backend.gotc.admin_auth export-checkpoint --data-dir /private/event --out /private/staging/organizer-totp.json`. This writes a new mode-0600 file. Existing destinations are refused. Install the map as described above, then remove the staging copy.
3. Run `python -m backend.gotc.admin_auth migrate-checkpoint --data-dir /private/event` with the intended credential view. Conversion verifies every original binding, preserves account identifiers, activation state and replay steps, rebuilds the table with secure deletion enabled, vacuums the development database and truncates its WAL. After interruption or insufficient disk space, stop other database users, free space and rerun the same command. A durable cleanup marker blocks ordinary startup and backups during incomplete scrubbing. After conversion, remove revoked seed entries from the delivered map and verify platform startup and a fresh named login.

The conversion cleans the current logical files. Historical copies, storage snapshots and remnants managed by the filesystem or storage device need independent retention or disposal. An older development binary that expects the seed column requires its original protected recovery set.

## Rollback

Before the first named portal login, a failed enrollment or confirmation leaves legacy access available. After that login, use a compatible forward fix or the named-account recovery procedure. An older application can bypass second-factor enforcement. Rehearse any code downgrade offline using the paired pre-enrollment database and credentials. Restoring an earlier database discards subsequent activity and may re-enable accounts or sessions. Restrict access during recovery and reconcile them before reopening.
