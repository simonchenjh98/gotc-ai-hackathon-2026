# Contestant upload acceptance

18 November 2026. Chromium 151.0.7922.34 completed all 11 browser journey groups against a temporary event bound to loopback. The contestant journey used the fingerprinted release frontend, the HTTP application, a new SQLite database and generated participant accounts. The browser fixture configured an unused loopback model-provider URL so it could display the team’s API key controls.

## Failure reproduced on the baseline

On `3a96a1804ba4`, a tester opened submissions in the disposable event, entered an issued team code, selected a synthetic PDF through the file picker and clicked the upload button. The server returned HTTP 200. The page reported an incomplete upload receipt and left the slide URL empty. Retrying would upload another file. The browser had rejected the HTTP URL generated by the local event. The draft and formal submission validator also required an HTTPS URL for the slides and ZIP fields.

Both validators now accept files served by the configured HTTP event. Before saving, the server matches an internal URL to the immutable upload row, team, material type, filename and stored file. External slide and ZIP links still require HTTPS. The upload API tests exercise the owned-file case, cross-team ownership, unexpected fields, incorrect file types and noncanonical URLs.

## Browser observations after the repair

| Action | Observed result |
| --- | --- |
| Enter the normal team code and navigate the contestant workspace | The same session accessed the team profile, private scores and provisioned API key form. The submission controls were disabled while the organizer’s window was closed. |
| Open the window and select PPTX, PDF and ZIP through the native file picker | Each file produced a download link. The browser downloaded the expected team-and-project filename with the correct extension. Downloaded bytes matched the original file, and the stored byte count and SHA-256 matched an independent calculation. The PDF superseded the PPTX in the slides field. |
| Attempt to replace the ZIP | The page rejected a file one byte above 100 MiB. A file named ZIP with invalid contents received HTTP 415. Closing the window after the form loaded caused HTTP 409 on upload. The existing ZIP link and unsaved project summary survived. Reopening and retrying the selected file produced a new link. |
| Save and reload the server draft | Draft v1 retained the project title, summary and both material URLs. A separately signed-in judge saw no formal submission. |
| Preview, confirm and check the receipt | The preview included clickable PDF and ZIP links. The page displayed the formal v2 receipt. Its request ID matched the stored successful submission and the URLs for both files. |
| Open the submitted materials as a judge | The judge saw the submitted summary and downloaded the PDF and ZIP with the expected filenames and bytes. |

The fixture used a minimal PPTX package, a Chromium-generated PDF and a ZIP containing a synthetic project directory. The size-limit case used a sparse local file. The run used synthetic data and did not access the production event or a model provider.

## Reproduction

Prepare the isolated Python environment and Chromium using the [browser acceptance instructions](../../tests/browser/README.md). From the repository root, run

```sh
python -B tests/browser/smoke.py --smoke-only
PYTHONPATH=tests/backend python -B -m unittest test_material_uploads
node --test tests/frontend/submission.test.mjs tests/frontend/draft-recovery-flow.test.mjs
```

An existing Chromium executable can be selected with `--chromium /path/to/chromium`. The upload HTTP suite passed all 21 tests. The two frontend suites passed all 71 tests. The [browser journey](../../tests/browser/contestant_upload.py) contains the file-picker actions, independent digest calculation, download comparisons and receipt checks. The [HTTP suite](../../tests/backend/test_material_uploads.py) covers the configured HTTP origin and external link policy.
