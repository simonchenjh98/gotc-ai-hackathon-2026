18 November 2026 · Organizer engineering report

The public site guides contestants through the event. The separate activity platform handles identity, submissions, competition results and AI services. The running release is the authoritative reference for the rebuild. On the audit date, 17 of 57 selected release files differed from organizer main after text line endings were normalized. These differences affect who can see results, what a contestant must submit, and who can enter finals.

## Frontend and backend by workflow

| Workflow | What people can do | What the service owns |
| --- | --- | --- |
| Public event site | Read the tracks, schedule, rubric and FAQs. Download the calendar, guide and checklist. Browse or filter the directory. | GitHub Pages hosts the information site. The directory reads the registration API on the event host. External event registration has its own form. |
| Team access and membership | Apply for a team, look up a claim, collect a participation code, and maintain the team's permitted profile fields. Existing registration-only credentials have a limited compatibility path. | Registration, roster matching, manual review, account binding, role checks, session rotation and team recycling. Organizer-assisted work has a distinct identity and audit trail. |
| Submission | Save drafts, recover local edits, review revisions, submit the presentation and project ZIP, and retrieve a receipt. Repository, demo, and descriptive fields are optional in the deployed formal-submission flow. | Team-scoped draft and formal versions, deadlines, conflict detection, receipts and history. Uploads enforce type, quota and size constraints. Linked Gitee repositories support commit previews and sealing. |
| Professional judging and voting | Judges save drafts, submit six-dimensional scores or recuse. Audience accounts vote. A contestant can check the results available to that team. | The service enforces voting limits, publication conditions, judge counts, revision checks and feedback visibility. The all-team professional board requires organizer access. |
| Exhibition and roadshow | Record exhibition feedback. Roadshow judges use the assigned roster, numeric rubric and project-progress field. Organizers review progress and confirm publication. | Stage-specific windows, frozen materials, revisions and exclusions. Three distinct formal judges qualify a roadshow score. Publishing normally selects up to 12 eligible teams by score with a deterministic tie break. An explicitly confirmed finalist roster takes precedence. |
| Finals and awards | Authorized judges select a seat, score finalists and nominate teams for awards. Organizers review completeness, confirm awards and publish results. | The deployed service expects **seven** judge seats. It owns eligibility, the finalist selection source, revisions, nominations, award allocation and publication state. |
| Organizer operations | Manage accounts and teams, inspect claim or submission history, configure deadlines and rosters, review records, preview imports and export results. | SQLite transactions, per-role authorization, audit records, conflict checks, CSV tooling and backup/restore utilities. Recycling preserves history and revokes access. |
| AI gateway | Teams manage their AI keys and inspect usage. Organizers configure model access and inspect activity and billing. | The gateway handles authentication, quotas, model routing, streaming and realtime connections, bounded uploads, media tasks, cancellation, usage and cost accounting. External provider availability and throughput were outside the local benchmark. |

| Deployed source, standings handler | 8.816 ms median, 9.019 ms p95 | Python 3.12, local synthetic SQLite database, 128 teams, eight judges, 1,024 audience accounts and 3,072 votes. Authenticated organizer handler, ten warm-ups and 50 sequential samples. Excludes HTTP/TLS and rendering. |

The core standings query counts votes for each team. Its existing vote key starts with the audience account ID, so looking up a team's votes scans unrelated rows. The frontend also loads organizer and finals code on the signed-out contestant screen. Both costs can be isolated and measured without changing event rules. The release serves ordinary static files through the Python handler with a no-store policy.

## Development and release boundaries

Organizer main has 21 HTML, JavaScript and CSS files at repository root. Frontend tests frequently read and slice the platform script as text. Backend tests share a directory with the service. The Pages publisher and installer each repeat knowledge of the public asset layout. A rewrite has to update those callers as well as application code.

Use separate frontend, backend, tests, operations and documentation directories. Keep the production URLs and SQLite contracts. Deliver browser code by route, narrow the standings read with measured database indexes, and exercise the real packaged application before considering release. Acceptance should cover signed-out and authenticated routes, team isolation, upload and receipt behavior, finals rules, database compatibility and a before/after run with the same synthetic workload.
