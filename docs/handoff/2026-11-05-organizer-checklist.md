## 开赛前的执行顺序

1. **容量先决。** 向活动方/Gitee 申请覆盖实际参赛人数的成员额度，或确认各队个人公开仓库方案。不要默认为可以无限邀请，也不要代下单付费。人数、实际成员权限和可用 API 应在扩容后复核。
2. **核准名录。** 使用已确认的队伍编号、队名和 Gitee 用户名；昵称不能唯一识别账号。私下维护名录，避免把提交码或私人联系方式放进公开仓库。
3. **建仓与授权。** 从模板创建 `team-编号-英文短名`，记录标准仓库地址和正式分支。主办方保留管理权，每位选手只获得本队开发所需权限。涉及敏感资源的新授权须在最终执行前核对具体对象与范围。
   自助申请接入后，在“组织仓库申请与恢复”中逐一核对用户名归属，勾选核对声明，再点“核对并批准建仓”。“核对恢复”和“刷新邀请”用于按状态核实外部结果，不能跳过账号核对。每队选择一个正式来源，另一平台仅作镜像。
4. **填写模板。** 补齐真实运行方式、AI 使用、测试、来源、局限和许可证，删除无用示例。实际公开前检查没有私密内容。
5. **分支规则验收。** 在测试仓库检查规则及分支状态是否都生效；只创建规则不等于分支已经受保护。免费套餐的限制、企业管理员全局权限和不同角色的行为都要实测。保护规则不替代代码归档。
6. **官网上线。** 在隔离副本完成队伍登录、草稿、正式提交、冲突、截止、回执查询、历史与旧评分回归，再按现有部署文档备份并发布。现有进行中的改动需选定明确的发布版本，不能把工作目录整体直接上传。
7. **设置窗口。** 录入真实队伍、生成独立提交码并私下发放，设置主办方确认的北京时间截止。未收到正式截止安排前保持关闭，不自拟截止时刻。
8. **演练。** 至少两支独立测试队伍，分别测试只能编辑本队、匿名读取公开材料、正确完整 SHA、错误 SHA 格式、重复请求、断网查询、关闭/截止和重新登录。记录真实结果，测试队伍不要混入正式名单。
9. **正式开放。** 先补充并验证每队上游请求限额和全局并发限制，当前代码审查仅认可受控单队试用。云端地址应真的出现作品提交入口；使用普通选手账号从外部网络走完整流程，再发放选手手册的可用版本。
10. **提交归档。** 从正式记录核对仓库与 SHA，独立保存对应代码及材料，并记下归档结果。不能把“已记录链接”标成“已备份代码”。

## 按 SHA 独立归档

此流程供获授权的主办方执行，尚未用于真实参赛提交。每次正式提交使用独立、不覆盖旧文件的目录。

1. 从官网的服务器回执复制队伍编号、正式版本、请求编号、完整 SHA 和服务器时间，登记标准仓库 URL。
2. 从指定仓库取得该完整 SHA，验证对象类型为 commit，并核对其与登记分支的关系；无法取得时记为失败、及时联系队伍，不用同名分支当前最新代码代替。
3. 保留完整 Git 对象备份与该 commit 的源代码归档。`git archive` 不会自动包含子模块代码、Git LFS 对象或外部依赖，需要单独保存并验证；模型、数据和第三方资源还要遵守原有授权边界。
4. 计算归档文件的 SHA-256，记录原仓库、完整 commit、官网版本/请求编号、服务器接收时间、归档时间和操作者。归档时间与官网接收时间分开记，不能回填伪装成同一时间。
5. 用归档解压副本按 README 复现，另存展示材料、视频和运行所需的获授权资源。归档目录仅供主办方使用，至少留一份独立备份。
6. 截止后关闭官网提交，再核对本轮评审快照。后续补交须经主办方明确处理，不静默替换已冻结材料。

## 后续自动化的验收边界

如继续接入“官网申请 → 组织建仓 → 绑定队伍 → 读分支 SHA → 预览 → 确认 → 回执/归档”，需另行完成：

- 实际公开 API 返回仓库 namespace.type=enterprise，普通 /orgs 查询返回 404；应使用官方 POST /enterprises/{enterprise}/repos，外部开源参数 private=1。使用明确作用域的服务端凭据，真实建仓和企业席位仍须验证，不自动切换到另一种建仓接口。
- 队伍绑定由服务端决定；选手不能指定别队身份，凭据不得发到浏览器或写入仓库。
- 并发申请、重试与失败有明确记录，避免重复建仓、错误授权或留下无人认领的仓库。
- 预览展示服务端取得的完整 SHA；确认时校验绑定和分支状态，分支发生推进则重新预览，不能悄悄提交另一版本。
- 原子保存官网回执与提交记录；归档失败明确提示和可重试，不宣称完整留存。
- 覆盖身份、权限、提交窗口、超时、竞态与上游故障，并在隔离仓库和生产环境分别验收。
